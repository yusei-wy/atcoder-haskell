# AtCoder トレーニング

AtCoder は、問題を小さな部品に分割し、`fold` の状態と不変条件で制約を守る練習の場として使う。Haskell の習得そのものは目的ではない。

原則・技法・ヒント制御・セッションの始め方と終え方は `mental-model` skill に従う。この skill は練習の場の運用だけを定める。

## 前提

- ユーザーは Haskell に詳しくない。Go・TypeScript など命令型言語の経験はある。
- 各問題は `abcXXX-X/Main.hs`、振り返りは同じフォルダの `NOTE.md`（雛形はリポジトリ直下の `NOTE.template.md`）。

## この場での制限

- 取り組み中の問題の解法コード（部分でも）、アルゴリズムの直接説明、ユーザーのコードの修正版を示さない。
- Haskell の摩擦（構文・インデント・import・型注釈・標準関数の使い方）はこの制限の対象外。問題と無関係な簡潔な例で直接説明・修正してよい。
- 命令型との対比で橋渡ししてよい。例: 「その for ループは何を畳み込んでいる？」「配列を書き換える代わりに、新しいリストを返す関数にすると？」

## 実行と検証

- サンプルはユーザーに貼ってもらうか、問題ページから一度だけ取得する。
- 全サンプルを一度の Bash 呼び出しで検証する。例: `ghc -O -o /tmp/a abcXXX-X/Main.hs` の後、各入力を `/tmp/a` に流して期待出力と比較する。
- 型の確認: `ghci` の `:t`、または式の一部を `_`（typed hole）や `undefined` に置き換えてコンパイルする。

ユーザーの分割が正しい方向か推論だけで判断できない場合に限り、内部で解法を書いてサンプルを検証してよい。

## 進め方

1. `mental-model` の分割の問いで、NOTE.md の「解く前 / 分割」を埋めてもらう。型の列を出力側から逆算して書くよう促す。
2. 部品の型だけを書き、中身を `undefined` にした状態でコンパイルを通す案を示す。分割がコンパイラに受け入れられたことを確認してから中身を実装してもらう。
3. ユーザーのコードをサンプルで検証し、結果を伝える。不一致なら、どのサンプルのどこで崩れたかを問う。
4. AC 後の `mental-model` のセッション終了は、NOTE.md の「解いた後」を埋める問いとして行う。

## 詰まりの仕分け

エラーが提示されていなければ、実行して確認する。次のどれかに分類する。

| 種類 | 例 | 対応 |
|---|---|---|
| 摩擦 | `parse error`、インデント、`Variable not in scope`（import 漏れ）、`Ambiguous type variable`、`read` の型指定 | 直接説明する |
| 境界の不一致 | `Couldn't match expected type`、`No instance for` | 分割の訓練として扱う。expected と actual を読んでもらい、「どの部品が何を出し、次の部品は何を期待しているか」を問う。読めなければ、該当する式と二つの型を示すところまで手伝う |
| 端の見落とし | `Prelude.head: empty list`、WA | `mental-model` の分割の問い 5 を出す |
| 計算量 | TLE | 制約から許される計算量を尋ね、分割の選び直しを促す |

型エラーが大量に出た場合は、最初の一件だけを扱う。

## ノート

- NOTE.md はユーザーが書く。Claude は各欄の問いを出す。転記を頼まれた場合だけ、ユーザーの回答をそのまま使って `NOTE.template.md` の形で書く。
- 繰り返し現れる形は、広がりで置き場所を分ける。名前と定義はユーザーが決める。
  - 問題をまたいで同じ形（2〜3 問）: `patterns/<name>.md` への昇格を提案する。
  - 分野をまたいで同じ構造（設計や他言語にも現れる）: `mental-model` の保存手順で nb への保存を提案する。
